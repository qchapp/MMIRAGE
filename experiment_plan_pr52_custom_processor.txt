## Context
PR #52 "Feature: Introduce Custom Processor for User Python Script Execution"
(https://github.com/LiGHTers-playground/MMIRAGE/pull/52, branch feature/custom_function)
adds a native `custom` processor to the MMIRAGE/AnonLib core:
- YAML-configurable: type: custom, script_path, function_name, max_workers, start_method
  (spawn default), timeout_ms, max_timeouts, max_errors, fallback_value
- pebble ProcessPool with spawn isolation; strict order preservation; soft-fail fallback
  injection; circuit breaker on max_timeouts/max_errors; immediate trip on fatal worker
  crash; local-import sys.path injection for the user script directory
- the user function receives the full current row as a dict and must return plain data
  (strings, numbers, lists, dicts, None)

## Does Plan B compare custom code per sample on BOTH sides including NeMo? YES.
Both frameworks execute the SAME user Python functions (normalize_query,
normalize_generated_answer) once per row/sample:
- AnonLib: the native `custom` processor runs the function in an isolated worker process
  per row.
- NeMo Curator/Data Designer: CustomColumnConfig with generation_strategy CELL_BY_CELL calls
  the generator function per cell (= per row).
The full original recipe (the one already benchmarked and committed) is re-expressed with
native custom-function support on both sides, so the comparison measures first-class
framework machinery on both frameworks. This closes the fairness gap that motivated Plan A
(the ~100-line benchmark-harness CustomProcessor shim in the AnonLib adapter disappears).

## Success criteria
- 1000/1000 schema-valid rows per repetition.
- Runtime within noise of the original run (~68.6 s vs ~131.2 s e2e).
- Footprint: AnonLib glue python drops to ~24 + adapter; declarative ~130.

## Risks / notes
- spawn pool startup per shard (small for 1 shard / 1000 rows).
- dict return values must be pickle-safe (they are: plain strings).
- timeout_ms default None (untimed) in the merged PR -> set explicit (e.g. 5000).
- custom processor counters are cumulative over the whole shard -> size max_timeouts and
  max_errors for 1000 rows, not per batch.
